# Task Management System (Django REST Framework)

## 1. Problem Statement
Individuals and small teams lose track of work when tasks live in chats and notes.
This project is a small **REST API** that stores projects, tasks, tags and user
profiles in a relational database, so tasks can be created, assigned, categorized,
filtered, searched and tracked from any client (here: Postman and Django Admin).

## 2. Features
- Full CRUD (create, list, retrieve, PUT, PATCH, delete) for Profiles, Projects, Tags and Tasks
- Relationships: OneToOne, ForeignKey (x2) and ManyToMany
- Field-level, object-level and model-level validation with clear error messages
- Duplicate prevention (tags, projects, profiles, tasks)
- Task filtering, searching and ordering (plus search/ordering on other resources)
- Page-number pagination (10 per page) on every list endpoint
- Customized Django Admin with inline tasks inside projects
- Postman collection with 65 requests and automated status checks

## 3. Technologies
Python 3.10+, Django 5.2, Django REST Framework 3.16, PostgreSQL, django-filter, python-dotenv, psycopg2-binary, Postman.

## 4. Database Models and Relationships
Exactly **four custom models**:

| Model | Fields | Purpose |
|---|---|---|
| `UserProfile` | user (OneToOne→User), phone, bio | Extra user info |
| `Project` | name, description, created_at | Groups tasks |
| `Tag` | name (unique) | Categorizes tasks |
| `Task` | title, description, status, priority, due_date, project, assigned_to, tags, created_at, updated_at | The work item |

| Relationship | Meaning |
|---|---|
| `UserProfile.user` → User (OneToOne) | one user, one profile (`user.profile`) |
| `Task.project` → Project (ForeignKey) | many tasks per project (`project.tasks`) |
| `Task.assigned_to` → User (ForeignKey, optional) | many tasks per user (`user.assigned_tasks`) |
| `Task.tags` ↔ Tag (ManyToMany) | many tags per task and many tasks per tag |

> **Important:** the ManyToManyField automatically creates a hidden join table
> (`tasks_task_tags`). It is generated by Django and is **not** a custom model, so the
> project still has exactly four custom models. Django's built-in `User` is used (no custom user model).

## 6. PostgreSQL Database Setup
1. Install PostgreSQL and remember the password of the `postgres` user.
2. Create the database (SQL Shell / `psql`, or pgAdmin → Create → Database):
```sql
CREATE DATABASE task_management_db;
```
3. Put the same name and your credentials in `.env` (next section). Django connects through
   `config/settings.py`, which reads `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`.

## 7. Installation Steps
```bash
python -m venv venv
venv\Scripts\activate            # Windows   (Linux/macOS: source venv/bin/activate)
pip install -r requirements.txt
```

## 8. Environment Configuration
Copy `.env.example` to `.env` (Windows: `copy .env.example .env`) and edit it:
```
SECRET_KEY=any-long-random-string
DEBUG=True
DB_NAME=task_management_db
DB_USER=postgres
DB_PASSWORD=your_postgres_password
DB_HOST=localhost
DB_PORT=5432
```
Never commit `.env` to Git.

## 11. API Endpoints
Each resource supports `POST` (create), `GET` (list), `GET /<id>/` (retrieve), `PUT /<id>/`, `PATCH /<id>/`, `DELETE /<id>/`.

| Resource | URL |
|---|---|
| UserProfile | `/api/profiles/` |
| Project | `/api/projects/` |
| Tag | `/api/tags/` |
| Task | `/api/tasks/` |

| Status code | Used for |
|---|---|
| 200 | successful GET / PUT / PATCH |
| 201 | successful POST |
| 204 | successful DELETE |
| 400 | validation error |
| 404 | object / page not found |

## 12. CRUD Examples (Task)
Create: `POST /api/tasks/`
```json
{
  "title": "Write report",
  "description": "First draft",
  "status": "Pending",
  "priority": "High",
  "due_date": "2030-12-31",
  "project": 1,
  "assigned_to": 1,
  "tag_ids": [1, 2]
}
```
- List: `GET /api/tasks/`  · Retrieve: `GET /api/tasks/1/`
- Full update: `PUT /api/tasks/1/` (send all fields)  · Partial update: `PATCH /api/tasks/1/` with `{"status": "Completed"}`
- Delete: `DELETE /api/tasks/1/`

Allowed values: `status` = `Pending`, `In Progress`, `Completed`; `priority` = `Low`, `Medium`, `High`.

## 13. Filtering, Searching, Ordering, Pagination
**Filtering** (exact match; tasks): 
`/api/tasks/?status=Pending` · `?priority=High` · `?project=1` · `?assigned_to=1` · `?status=Pending&priority=Low`

**Searching:** `/api/tasks/?search=assignment` (title and description). Also: projects (`name`, `description`), tags (`name`), profiles (`username`, `phone`, `bio`).

**Ordering:** `/api/tasks/?ordering=-created_at` · `?ordering=due_date` · `?ordering=-priority` (High first; priority is sorted Low < Medium < High, not alphabetically). Prefix `-` = descending. Also available on projects (`name`, `created_at`), tags (`name`), profiles (`id`, `phone`).

**Pagination:** 10 items per page, `?page=2` for the next page.
```json
{ "count": 30, "next": "http://127.0.0.1:8000/api/tasks/?page=2", "previous": null, "results": [] }
```

## 15. Validation Error Examples
All return `400 Bad Request`.

| Request | Response |
|---|---|
| Empty title | `{"title": ["Task title cannot be empty."]}` |
| `"status": "Done"` | `{"status": ["\"Done\" is not a valid choice."]}` |
| Past due date | `{"due_date": ["Due date cannot be in the past."]}` |
| Missing project | `{"project": ["A task must belong to a project."]}` |
| Project id 999999 | `{"project": ["Project with id 999999 does not exist."]}` |
| High priority, no due date | `{"due_date": ["High priority tasks must have a due date."]}` |
| Same title in same project | `{"title": ["This project already has a task with this title."]}` |
| Duplicate tag | `{"name": ["Tag 'Urgent' already exists."]}` |
| Second profile for a user | `{"user": ["This user already has a profile."]}` |
| Bad phone | `{"phone": ["Enter 7-15 digits, optionally starting with '+'."]}` |

## 16. Postman Testing
1. Start the server (`python manage.py runserver`) and make sure a superuser exists (user id `1`).
2. Postman → **Import** → select `Task_Management_API.postman_collection.json`.
3. Open the collection → **Variables** tab: `base_url` is `http://127.0.0.1:8000`; change `user_id` if your user id is not 1.
4. Click **Run** on the collection and run the folders **in order**: `1 - UserProfile`, `2 - Tag`, `3 - Project`, `4 - Task`.
   Each create request saves its id (`profile_id`, `tag_id`, `project_id`, `task_id`) into collection variables automatically.
5. Every request has a test that checks the expected status code (shown in the Test Results tab).

Each folder contains: Create, List, Retrieve, PUT, PATCH, search/ordering/pagination examples, duplicate-prevention and validation-error examples, and Delete. Tags and Projects are deleted using a temporary record so the main `tag_id` / `project_id` stay valid for the Task folder.
